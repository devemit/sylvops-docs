## User-visible changes from preview.10

### Session status now separates lifecycle, activity, and attention

- The old single Session state is replaced by three independent daemon-owned dimensions: lifecycle (`fresh`, `starting`, `running`, `exited`, `failed`, `terminated`, `disconnected`), Provider activity (`none`, `working`, `awaiting_input`, `completed`, `interrupted`, `recoverable_failure`), and one latest Attention Event. Attention reasons are input requested, successful completion, recoverable failure, and terminal failure, with pending/acknowledged/resolved state and a monotonic per-Session identity. Invalid or unknown combinations fail closed. See the candidate [state model](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-core/src/session_state.rs) and [protocol history](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/docs/architecture/ipc.md).
- A completed Codex or Claude turn can now remain a live, attachable Session while showing successful-completion attention. User interruption is distinct and does not look like successful completion. Active subagents, background tasks, scheduled work, or exhausted tracking capacity suppress premature completion. Process and Provider terminal signals deduplicate against an already-recorded completion. See the candidate [status reducer](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-core/src/status.rs) and [status-hook contract](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/docs/architecture/status-hooks.md).
- The TUI has a durable **Needs Attention** group covering all four reasons, ordered by urgency and then recency. A pending Session is omitted from Active Sessions; a still-live Session returns there after completion is acknowledged. Opening completion or terminal-failure history acknowledges that exact event; merely opening an input request does not clear it; recoverable failures have an explicit **Dismiss** action. See [PR #186](https://github.com/devemit/sylvops/pull/186), the candidate [TUI grouping](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-tui/src/app.rs), and [rendered controls](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-tui/src/render.rs).

### Resume follows a persisted Session lineage

- Resume is now daemon-authoritative and lineage-aware in both TUI and desktop. Opening any predecessor follows its persisted successor chain to the leaf. A live leaf is attached without creating anything; an eligible terminal leaf creates and attaches exactly one successor; concurrent attempts converge on the same successor. Historical attempts remain visible and derived attempt markers do not mutate the user's Session name. See [PR #188](https://github.com/devemit/sylvops/pull/188), [PR #189](https://github.com/devemit/sylvops/pull/189), and the candidate [daemon resume implementation](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-daemon/src/daemon.rs).
- Eligibility applies to exited, failed, user-terminated, or disconnected Codex and Claude Sessions and still requires a verified Conversation identity, a healthy resume-capable Provider, and the same valid Worktree. When unavailable, the daemon returns one typed reason, retained history remains available, and **Start Fresh** is a separate action. A failed successor launch remains the newest historical leaf and can be retried later. See the candidate [resume protocol](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-core/src/protocol.rs), [Claude contract](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/docs/providers/claude.md), and [PR #192](https://github.com/devemit/sylvops/pull/192).

### Attention notifications are coordinated across desktop and TUI

- Newly created live Attention Events for input, completion, recoverable failure, or terminal failure can produce one daemon-granted delivery claim across all connected clients. Existing events at startup/reconnect remain visible but are not replayed. Native-notification and sound preferences are independent, persisted, shared, enabled by default, and exposed in TUI settings. See [PR #190](https://github.com/devemit/sylvops/pull/190), the candidate [attention contract](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-core/src/attention.rs), and [TUI settings](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-tui/src/render.rs).
- A client reports only its foreground Session. If that exact Session is visibly foregrounded, external notification and sound are suppressed across clients; viewing another Session does not suppress the alert. Visible completion and terminal failure are acknowledged automatically, while input and recoverable failure remain pending under their reason-specific rules. Claims are best-effort and at-most-once: a vanished claimant or presentation failure is not replayed, while durable Needs Attention remains the fallback. See [PR #194](https://github.com/devemit/sylvops/pull/194) and the candidate [protocol 1.30 contract](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/docs/architecture/ipc.md).
- Desktop and TUI now attempt native delivery on Windows, macOS, and graphical Linux. Windows uses notification-area balloons and `MessageBeep`; macOS uses fixed `/usr/bin/osascript` and `/usr/bin/afplay`; Linux requires a graphical display and tries fixed `/usr/bin/notify-send`, with fixed `canberra-gtk-play` or `paplay` sound fallbacks. Missing tools, services, displays, or permissions degrade to in-client presentation without changing Session state. See [PR #191](https://github.com/devemit/sylvops/pull/191), [PR #193](https://github.com/devemit/sylvops/pull/193), and the candidate [desktop](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-desktop/src/notifications.rs) and [TUI](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-tui/src/notifications.rs) adapters.
- Notification payloads contain only the bounded, control-character-stripped Session display name and bounded Attention Reason. They exclude prompts, terminal output, raw errors, repository/path data, and Work Source content. Presentation queues and subprocesses are bounded and nonblocking; failure never changes the underlying attention or Session outcome. See the candidate [daemon notification tests](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-daemon/tests/attention_notifications.rs).

### Provider lifecycle and cleanup regressions are fixed

- Windows Codex Conversation identity capture is restored by serializing the already-canonical relay executable as a normal drive/UNC path accepted by `cmd.exe`, while rejecting command-expansion characters and keeping relay arguments fixed. This makes later exact resume possible on Windows, including installs under paths with spaces and non-ASCII characters. See [PR #184](https://github.com/devemit/sylvops/pull/184) and the candidate [Codex contract](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/docs/providers/codex.md).
- SylvOps now tolerates Codex's narrowly recognized trust metadata in an otherwise owned runtime profile, so normal process-exit cleanup and Delete Session do not leak or become blocked by Codex's own safe mutation. Unknown edits still fail closed, and only provably owned stale profiles are removed. See [PR #183](https://github.com/devemit/sylvops/pull/183).
- The daemon drains authenticated hook connections and accepted deliveries before finalizing a provider process that exits quickly, preventing a valid late lifecycle/identity event from being discarded at the process-exit boundary. See [PR #200](https://github.com/devemit/sylvops/pull/200).

## Compatibility, persistence, and authority implications

- The local IPC protocol advances from minor 23 to 30 across staged changes for expanded status, interruption, dismissal/acknowledgement, removal of legacy state, lineage resume, notification claims/preferences, and cross-client focus coordination. Exact-version handshakes reject incompatible clients with both versions in the diagnostic, so the daemon, desktop, TUI, and CLI must be upgraded together. [Candidate IPC contract](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/docs/architecture/ipc.md).
- Database migrations 9 and 10 transactionally add validated bounded status JSON, convert legacy seen/unseen completion into acknowledged/pending attention, clear all persisted process identities, then remove the legacy `state` column. Records with a stored process identity become disconnected instead of being trusted as live. Startup refuses unknown newer schemas; downgrading to preview.10 after opening the database with preview.11 is therefore not a supported compatibility path. See the released [migration 9](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-daemon/migrations/0009_expanded_session_state.sql), [migration 10](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/crates/sylvops-daemon/migrations/0010_contract_session_status.sql), and [persistence contract](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/docs/architecture/persistence.md).
- Notification delivery adds only local presentation authority. It does not send remote push notifications or Provider content, does not alter Session state on delivery failure, and delegates quiet-time/do-not-disturb behavior to the operating system. Notification activation opens retained history and does not itself resume or start a provider. See the closed parent specification [Issue #167](https://github.com/devemit/sylvops/issues/167) and [PR #191](https://github.com/devemit/sylvops/pull/191).

## Documentation implications

- Replace preview.10 in the current-version, installation, and update pages; use the exact preview.11 release URL and asset names, and keep checksum verification tied to the same release.
- Document the new Session vocabulary and behavior: live completion is still active/attachable; Needs Attention contains four reasons; acknowledgement/dismissal rules differ by reason; successful completion is no longer equivalent to process exit.
- Update resume documentation from “open an inactive Session” to lineage semantics: any predecessor resolves to the latest leaf; live leaves attach; eligible terminal leaves create one successor; exact refusal reasons preserve history; Start Fresh is separate.
- Replace preview.10's input-only notification wording with daemon-coordinated, cross-client notifications for all four Attention Reasons, shared independent notification/sound preferences, foreground suppression, no startup replay, privacy limits, and platform fallbacks. Avoid promising clickable activation on platforms whose command adapter cannot report clicks.
- The released README is stale in two contradictory ways: it still calls preview.6 the current build and still says notifications are planned, while a later main-only README commit calls preview.10 current. Public docs should use the released source and final release metadata, not either stale current-version sentence. [Released README](https://github.com/devemit/sylvops/blob/86b009bde7c71d70c69616e282158f0b945c86e2/README.md), [later unshipped README commit](https://github.com/devemit/sylvops/commit/548a29a855bde321cf4cf520171694d1881bb9de).
